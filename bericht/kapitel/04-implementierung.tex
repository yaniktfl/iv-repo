\section{Implementierung}\label{sec:implementierung}

\subsection*{Gesamtaufbau}

Die Anwendung ist als \texttt{Browser.element} nach den Prinzipien der Elm-Architektur aufgebaut \cite{ElmArchitecture}. Die Zustandsverwaltung basiert auf einem zentralen \texttt{Model}, einem gemeinsamen \texttt{Msg}-Typ sowie getrennten \texttt{update}- und \texttt{view}-Funktionen. Der Quellcode verteilt sich auf sechs Elm-Module sowie ein vorbereitendes Python-Skript (Tabelle~\ref{tab:module}).

Die Aufgaben der Module sind voneinander abgegrenzt: \texttt{Data.elm} enthält Typdefinitionen, JSON-Decoder und Filterfunktionen für die Datensätze. Die Module im Verzeichnis \texttt{Views/} berechnen die jeweilige SVG-Darstellung. Sie greifen weder direkt auf das globale Modell noch auf den konkreten \texttt{Msg}-Typ der Anwendung zu. Stattdessen definiert jedes Visualisierungsmodul einen eigenen Konfigurationsrecord (\texttt{Config msg}), über den \texttt{Main.elm} den benötigten Zustandsausschnitt und passende Callback-Funktionen übergibt (Listing~\ref{lst:config}).

\begin{lstlisting}[caption={Config-Record der Heatmap: Zustandsausschnitt und Callbacks},label={lst:config}]
type alias Config msg =
    { hoveredDay : Maybe String
    , selectedDays : List String
    , onHoverDay : String -> Tooltip -> msg
    , onMove : Float -> Float -> msg
    , onLeave : msg
    , onToggleDay : String -> msg
    }
\end{lstlisting}

Durch die Parametrisierung über den Typparameter \texttt{msg} bleiben die einzelnen Visualisierungsmodule von der übrigen Anwendungslogik entkoppelt. Das erleichtert das Testen sowie eine spätere Wiederverwendung der Komponenten. Die Aufrufe in \texttt{Main.view} erfordern zwar zusätzliche Konfigurationsobjekte, dafür sind Ereignisbehandlungen für Mausbewegungen und Klicks zentral in \texttt{Main.elm} zusammengeführt.

\subsection*{Datenstrukturen}

Der Zustand der Benutzeroberfläche und der Interaktionen wird im zentralen Record \texttt{Model} geführt (Listing~\ref{lst:model}). Die gewählten Datentypen orientieren sich an den funktionalen Anforderungen der Oberfläche.

\begin{lstlisting}[caption={Zentrales Model mit allen Interaktionszuständen},label={lst:model}]
type alias Model =
    { dataset : Result String Dataset   -- Decoder-Fehler explizit im Typ
    , selectedMonths : Set Int          -- Menge: Mehrfachauswahl von Monaten
    , hoveredDay : Maybe String         -- fluechtiger Fokus (Hover)
    , selectedDays : List String        -- dauerhafte Auswahl, Reihenfolge zaehlt
    , tooltip : Maybe Tooltip           -- Position und Inhalt am Mauszeiger
    , brushes : Dict Int ( Float, Float )  -- Achsenindex -> Wertanteil lo..hi
    , dragging : Maybe ParallelCoordinates.Drag  -- laufender Brush-Vorgang
    }
\end{lstlisting}

Die einzelnen Felder des Modells erfüllen dabei spezifische Aufgaben: \texttt{selectedMonths} verwendet ein \texttt{Set Int}, wodurch beliebige Kombinationen mehrerer Monate ausgewählt werden können. Für die ausgewählten Tage (\texttt{selectedDays}) kommt eine \texttt{List String} anstelle einer Menge zum Einsatz. Dadurch bleibt die Reihenfolge der Benutzerklicks erhalten, sodass der zuletzt ausgewählte Tag im Detailpanel als primäre Referenz angezeigt werden kann. Das Wörterbuch \texttt{brushes} speichert relative Wertebereiche zwischen 0 und 1 bezogen auf die jeweilige Achsenhöhe. Das stellt sicher, dass gesetzte Filterbereiche auch bei einer Neuskalierung der Achsen nach einem Monatswechsel erhalten bleiben. Der laufende Ziehvorgang wird im Feld \texttt{dragging} separat gehalten, damit die Filterung während der Mausbewegung kontinuierlich aktualisiert werden kann, ohne die zuvor gespeicherten Werte vorzeitig zu überschreiben. Das Feld \texttt{dataset} kapselt den Datensatz in einem \texttt{Result}, wodurch etwaige Ladefehler zur Laufzeit im Interface abgefangen und dargestellt werden können.

Für die Messwerte selbst existieren die beiden Datenstrukturen \texttt{Hourly} mit 14 Feldern und \texttt{Daily} mit 13 Feldern. Die Bereitstellung voraggregierter Tageswerte vermeidet aufwendige Gruppierungen zur Laufzeit der Visualisierungen. Im Typ \texttt{Hourly} ist das Feld \texttt{priceEurMwh} als \texttt{Maybe Float} definiert, da für einzelne Stunden keine Börsenpreise vorliegen und dieser Umstand in den Ansichten explizit berücksichtigt werden muss.

Weil beide Strukturen mehr als acht Felder umfassen, die Kernbibliothek \texttt{elm/json} jedoch Dekoderfunktionen nur bis \texttt{map8} anbietet, wurde eine Hilfsfunktion \texttt{andMap} implementiert (Listing~\ref{lst:andmap}). Sie erlaubt es, Dekoder für umfangreichere Records sequentiell zusammenzusetzen, ohne zusätzliche externe Abhängigkeiten einzubinden.

\begin{lstlisting}[caption={andMap erweitert map8 auf beliebig viele Felder},label={lst:andmap}]
andMap : Decoder value -> Decoder (value -> result) -> Decoder result
andMap valueDecoder functionDecoder =
    Decode.map2 (\fn value -> fn value) functionDecoder valueDecoder
\end{lstlisting}

\subsection*{Umsetzung der Visualisierungen}

Die grafische Ausgabe aller drei Hauptansichten wird mittels \texttt{elm-community/typed-svg} als SVG erzeugt. Durch typisierte Attribute werden fehlerhafte Attributnamen oder fehlende Einheiten bereits bei der Übersetzung vom Elm-Compiler abgefangen.

Die Monatsübersicht in \texttt{Views/TimeSeries.elm} berechnet aus der Liste der Tageswerte über die Funktion \texttt{monthly} zwölf monatliche Zusammenfassungen. Zeiträume ohne vorliegende Messwerte werden per \texttt{filterMap} übersprungen, damit sie im Diagramm nicht fälschlich als Nullwerte erscheinen. Die Balkenhöhe bildet Anteile von 0 bis $130\,\%$ linear ab. Die Skalierung der überlagerten Preislinie orientiert sich am minimalen und maximalen Börsenpreis des gewählten Zeitraums, sodass sich die Preisachse bei Filteränderungen dynamisch anpasst.

Die Stunden-Heatmap in \texttt{Views/Heatmap.elm} baut ihre Zeichenfläche schichtweise auf: Unter den Datenzellen liegt ein vollständiges Raster aus grauen Platzhalterzellen für sämtliche Stunden des Jahres. Wo Messwerte vorliegen, überdecken die farbigen Zellen diesen Hintergrund. Fehlen Stundenwerte in den Daten, bleibt die graue Hintergrundzelle sichtbar. Auf diese Weise werden Datenlücken visuell ausgewiesen, ohne dass dafür Sonderregeln bei der Iteration erforderlich sind. Die Farbzuordnung berechnet aus dem Erneuerbarenanteil über eine kontinuierliche Interpolationsfunktion RGB-Werte (Listing~\ref{lst:color}). Anteile bis $120\,\%$ werden farblich differenziert, während Spitzenwerte darüber auf den oberen Farbbereich abgebildet werden.

\begin{lstlisting}[caption={Farbrampe der Heatmap: Begrenzung bei 120\,\% statt Kappen der Daten},label={lst:color}]
renewableColor : Float -> Color.Color
renewableColor value =
    let
        t = clamp 0 1 (value / 120)
        r = 0.12 + (1 - t) * 0.72
        g = 0.25 + t * 0.47
        b = 0.42 + (1 - abs (t - 0.5) * 2) * 0.2
    in
    Color.rgb r g b
\end{lstlisting}

Das Modul \texttt{Views/ParallelCoordinates.elm} erzeugt die parallelen Koordinaten aus einer Liste von Achsendefinitionen. Jeder Eintrag enthält die Beschriftung, eine Zugriffsfunktion auf das jeweilige Datenfeld sowie den Wertebereich. Zur Filterung prüft die Funktion \texttt{passesBrushes} jeden einzelnen Tag über \texttt{List.all} gegen alle aktiven Filterbereiche der Achsen, was einer logischen UND-Verknüpfung entspricht.

\subsection*{Interaktionslogik und Koordinatenverarbeitung}

Ereignisse der Oberfläche werden über zwölf Konstruktoren im \texttt{Msg}-Typ abgebildet und in der zentralen \texttt{update}-Funktion verarbeitet. Die visuelle Synchronisation erfolgt über den gemeinsamen Modellzustand: Wenn eine Benutzeraktion den Zustand in \texttt{Main.elm} verändert, erhalten die abhängigen Ansichten im nachfolgenden Renderdurchlauf die neu gefilterten Daten.

Eine wichtige Rolle bei den parallelen Koordinaten spielt das interaktive Brushing, das Bildschirmkoordinaten der Maus in Wertebereiche der jeweiligen Achsen übersetzt. Da dynamische Abfragen der Elementmaße über \texttt{getBoundingClientRect} in Elm zusätzliche asynchrone Befehle erfordern würden, wird die SVG-Grafik mit einer festen Abmessung von $1280 \times 450$\,Pixeln gerendert. Dadurch entspricht der vertikale Versatz \texttt{offsetY} des auslösenden Mausereignisses unmittelbar der Koordinate im SVG-System. Die Umrechnung der Koordinate in einen relativen Wert zwischen 0 und 1 erfolgt über die Funktion \texttt{yToFraction} (Listing~\ref{lst:brush}).

\begin{lstlisting}[caption={Umrechnung der Mausposition in einen normierten Achsenwert},label={lst:brush}]
yToFraction : Float -> Float
yToFraction offsetY =
    1 - clamp 0 1 ((offsetY - marginTop) / innerH)
\end{lstlisting}

Die Filterung durch Brushing wirkt sich über die parallelen Koordinaten hinaus auch auf die Heatmap und die Kennzahlenleiste aus. Die Zuordnung von Pixelkoordinaten zu Datumsbereichen verbleibt im Modul \texttt{ParallelCoordinates.elm}: Die Funktion \texttt{matchingDates} ermittelt jene Tage, die innerhalb aller gesetzten Filtergrenzen liegen. Das Hauptmodul \texttt{Main.elm} greift auf diese Datumsmenge zu und aktualisiert die übrigen Komponenten. Auch temporäre Änderungen aus dem laufenden Ziehvorgang fließen direkt in diese Auswertung ein, wodurch eine kontinuierliche Filterung während der Mausbewegung erreicht wird.

Für eine konsistente Koordinatenberechnung in unterschiedlichen Webbrowsern erstreckt sich die unsichtbare Trefferfläche jeder Achse über die volle Höhe von $y = 0$ bis zum unteren Rand. Dies verhindert, dass einzelne Browser \texttt{offsetY} relativ zur Oberkante eines kleineren inneren Elements berechnen. Während eines aktiven Ziehvorgangs legt die Anwendung zudem ein transparentes Rechteck über die gesamte Diagrammfläche. Dieses nimmt Ereignisse für Mausbewegungen (\texttt{mousemove}) sowie das Loslassen der Maustaste (\texttt{mouseup}) entgegen, sodass die Filterung auch dann fortgeführt wird, wenn der Zeiger die schmale Achsenlinie kurzzeitig verlässt.

\subsection*{Implementierungsaufwand}

Beim Aufbau der Anwendung konnte teilweise auf Vorarbeiten und Entwurfsmuster aus den vorangegangenen Übungsaufgaben aufgebaut werden. Dies betraf vor allem die grundlegende Struktur der Elm-Architektur, einfache Skalierungsfunktionen für Achsen und Gitter sowie Interaktionen wie das Umschalten von Monatsfiltern und Hervorhebungen beim Überfahren mit dem Mauszeiger.

Einen spürbaren Arbeitsaufwand erforderte hingegen die Aufbereitung der Rohdaten im Vorfeld. Die Tabellen der Energy-Charts-Schnittstelle enthielten einige Besonderheiten: Bestimmte als Gigawatt deklarierte Spalten enthielten tatsächlich Megawattwerte oder wiesen Lücken auf, was erst durch Plausibilitätsprüfungen auffiel und eine manuelle Rekonstruktion der Residuallast im Datenabrufskript nötig machte. Auch die Syntax der API verlangte eine genaue Differenzierung zwischen numerischen Filtern über \texttt{where\_} und Zeichenkettenvergleichen über das Feld \texttt{filters}.

Innerhalb der Elm-Anwendung war das Brushing der parallelen Koordinaten der aufwendigste Teil. Ein früher Entwurf mit vollständig responsiver SVG-Skalierung führte dazu, dass die berechneten Filtergrenzen abhängig von der Browserfensterbreite von den tatsächlichen Mauspositionen abwichen. Erst die Festlegung auf eine feste Diagrammbreite, kombiniert mit vollflächigen Trefferflächen und einem transparenten Interaktions-Overlay, gewährleistete ein stabiles Verhalten. Ebenso verlangte die Darstellung von Datenlücken in der Heatmap eine gezielte Lösung: Ein simples Weglassen unvollständiger Stunden hätte benachbarte Zellen zusammengeschoben und die zeitliche Zuordnung der Tage verfälscht. Gelöst wurde dies durch das vorab gerenderte Gitter aus neutralen Hintergrundzellen.

Im Bereich der Datenverarbeitung innerhalb von Elm erforderte der Umfang der Datensätze zudem die Erweiterung der Standard-Decoder über die Bibliotheksgrenze von acht Feldern hinaus.

Bezüglich der Rechenleistung erzeugt die Anwendung im ungefilterten Zustand etwa $8\,690$ Datenzellen, $8\,784$ Hintergrundelemente und $364$ Linienzüge als SVG. Da aufwendige Aggregationen vorberechnet vorliegen und Zustandsänderungen im Elm-Modell nur gezielte Aktualisierungen im DOM auslösen, läuft die Interaktion im Browser ohne wahrnehmbare Verzögerungen ab. Bei einer Ausweitung auf mehrjährige Datenbestände in voller Stundenauflösung wäre mittelfristig ein Wechsel von SVG zu HTML5-Canvas ratsam.

Zur Absicherung gegen Ausfälle sind Fehlerbehandlungen auf zwei Ebenen eingerichtet: Ein Scheitern des HTTP-Ladevorgangs wird durch das einbettende Skript abgefangen und gemeldet. Kann die JSON-Datei zwar geladen, aber nicht erfolgreich in die internen Typen überführt werden, gibt Elm die detaillierte Fehlermeldung des Decoders im Browserfenster aus.

\subsection*{Einsatz von KI-Werkzeugen}

Einzelne Abschnitte des Quellcodes wurden unter Verwendung von KI-Sprachmodellen erstellt. Die Nutzung konzentrierte sich dabei auf Entwürfe für JSON-Decoder, mathematische Hilfsfunktionen wie die Umrechnung von SVG-Koordinaten sowie das Erstellen wiederkehrender Elm-Templates.

Die konzeptionellen Entscheidungen, die Modulstruktur sowie die fachliche Ausgestaltung des Projekts erfolgten eigenständig. Hierzu gehören die Auswahl und Begründung der drei Visualisierungsansätze, die Anordnung der Dimensionen im Koordinatendiagramm, die Farbskalierung für Werte über $100\,\%$ sowie die Methodik zur Visualisierung unvollständiger Zeitreihen.

Generierte Codevorschläge wurden vor der Integration systematisch überprüft:
\begin{itemize}
    \item Syntaktische und typbezogene Validierung durch den Compiler (\texttt{elm make}),
    \item Abgleich der im Frontend dargestellten Summen und Mittelwerte mit unabhängig in Python berechneten Vergleichswerten,
    \item Manuelle Überprüfung aller Benutzerinteraktionen und Randfälle im Browser.
\end{itemize}

Die verwendeten Prompts und Korrekturschritte sind im Anhang gemäß den Richtlinien des Moduls aufgeführt.
